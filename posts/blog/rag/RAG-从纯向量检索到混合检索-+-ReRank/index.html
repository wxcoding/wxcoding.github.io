RAG 从纯向量检索到混合检索 + ReRank

更新于 2026年10月25日 · 发布于 2026年3月9日
|编辑此页

从纯向量检索到混合检索 + ReRank：个人 RAG 问答系统踩坑与总结

背景：用 Spring Boot 3.4 + Spring AI + Vue 3 做了一个防诈骗知识问答系统（llm-afs）。以知识库文档和诈骗案例为可信数据源，通过 RAG 把检索结果注入通义千问的提示词，提供带引用来源的流式多轮问答。

一、最终检索链路

初版是“文档入 pgVector，余弦相似度 Top-K，拼进 Prompt”的纯向量检索，经过几轮重构后定型为「查询改写 → 双路召回 → RRF 融合 → ReRank 精排」：

用户问题
  ├─ 原始查询 ──────────────→ 向量召回 Top-20 ─┐
  └─ 同义词扩展 + 口语化改写 → 全文召回 Top-20 ─┤
                                                ├─ RRF 融合 (K=60)
                                                ↓
                                        ReRank 候选池 Top-20
                                                ↓
                                          截取 Top-5
                                                ↓
                                  拼装上下文 + 最近 10 条历史 → LLM 流式生成

二、踩坑

坑 1：纯向量检索搞不定“用户用词和文档用词不一致”

初版上线后最明显的问题：用户问“我被骗了钱能追回来吗”，知识库里明明有《电信网络诈骗资金追回流程》，向量检索却捞不上来。

原因是 Embedding 模型对语义相关但用词不同的场景没那么神——“被骗” vs “诈骗”、“怎么办” vs “处理流程”、“追回” vs “挽损”，向量距离并不近。反诈这个垂直领域尤其严重：用户全是口语化表达，文档全是书面语。

解法：不要指望单一通道。向量检索负责语义泛化，关键词检索负责精确命中，两路互补：

  • 查询扩展只做词典式改写：维护反诈领域同义词表（“被骗”→“上当/被坑/遭遇诈骗”）和口语→书面映射（“能追回吗”→“能否追回 挽回损失”），见 DictionaryQueryExpander.java。
  • 关键细节：扩展查询只喂给关键词通道，向量通道仍然用原始问题。扩展词会稀释语义向量，这是试出来的教训。

坑 2：PostgreSQL 全文检索对中文基本是“开箱不可用”

想做 BM25 风格的的关键词召回，第一反应是用 PostgreSQL 自带的 to_tsvector。踩坑点：

  • 默认配置对中文不分词，整段中文会被当成一个词，查询永远匹配不上。
  • 引入 zhparser 等第三方分词插件意味着部署依赖变重，且分词行为不在应用代码控制内，查询侧和索引侧容易不一致。

解法：确定性分词器，写入和查询共用同一份代码，见 FullTextTokenizer.java：

  • 连续中文按**重叠二元词（bigram）**切分——“网络诈骗”切成 网络 / 络诈 / 诈骗，这样查询“诈骗”也能命中“网络诈骗”。
  • 英文数字序列统一小写。
  • 索引侧把分词结果写进 search_text，用 generated column 自动维护 tsvector，挂 GIN 索引（见 V12__use_postgresql_full_text_search.sql）。

这里其实还有一段演进：V11 版本是把词项存成数组、查询时用数组交集匹配，功能能跑但没法用 GIN 索引、排序也粗糙，V12 才改成 tsvector 生成列。教训：检索基础设施一步到位用数据库原生能力，别自己造中间格式。

坑 3：两路召回的分数不能直接相加

向量通道产出的是余弦距离（0~1，越小越好），全文检索产出的是 ts_rank_cd 相关性分（量级飘忽，越大越好）。两者量纲完全不同，加权求和就是玄学调参，今天调好明天换个模型全废。

解法：RRF（Reciprocal Rank Fusion），只用排名，不用分数：

score(chunk) = Σ 1 / (K + rank_channel(chunk))    K 取经验值 60

实现里还有几个容易翻车的细节，都在 PostgresHybridSearchService.java：

  • 两路必须共用同一套 chunk ID。入库时用 sourceType:sourceId:index 生成确定性 UUID（UUID.nameUUIDFromBytes），向量库和 rag_chunk 表写同一个 ID，融合时才能按 ID 对齐累加。
  • 同一通道内去重：多个扩展查询命中同一个 chunk 时，只保留它的最佳名次，否则等于给扩展词多的查询偷偷加权。
  • 融合后批量回表取原文和元数据，别逐条查。

坑 4：把 ReRank 当银弹

RRF 融合后的 Top-20 已经不错，但头部精度还是差口气——反诈场景里“相似的无关”特别多（都是“诈骗”，但一个是刷单诈骗一个是贷款诈骗）。

于是加了 ReRank 精排（千问 qwen3.7-text-rerank，交叉编码器，query 和文档一起进模型打相关性分）。这一层的定位要非常清醒：

  • ReRank 是增强层，不是召回的替代品。它只对粗召回的 Top-20 重排，不扩大召回面。召回烂，精排无力回天。
  • ReRank 必须可开关、可降级：API 挂了、响应格式变了（索引越界、重复 index），保留原始排序继续走，见 RerankService.java。
  • 候选池 20 → 精排后保留 5。上下文窗口寸土寸金，塞多了反而引入噪声、拉高 token 成本。

坑 5：两个“低级”事故

这两个坑不在检索算法里，但直接影响可用性：

  1. Embedding 同步失败把服务拖垮。初版启动时同步向量库，API Key 没配或网络抖动直接启动失败。改成只记告警、正常启动，问答退化为纯 AI 对话。外部模型调用永远不应该是应用启动的硬依赖。
  2. SSE 流式前端长时间空白。本地好好的，上 Nginx 就白屏——proxy_buffering 默认开启，SSE 数据被缓冲住了。关掉缓冲、调大 proxy_read_timeout 才解决。流式系统联调时，中间每一层代理都是嫌疑犯。

坑 6：流式生成的“静默失败”

还有一个隐蔽的坑：思考型模型有时只输出 reasoning_content、正文为空，流正常结束但不产出任何内容——onErrorResume 不会触发，前端就是一片空白。必须在流结束时显式检查“有没有收到有效内容”，没有就走降级文案，而且降级文案也要按正常 SSE 分块节奏流式发出，保持前端渲染逻辑一致。

三、多级降级链

RAG 系统的外部依赖太多了：Embedding API、Chat API、ReRank API、向量库、全文索引。任何一环挂掉都不能让用户看到错误页。最终固化的降级链：

混合检索异常   → 退回纯向量检索
ReRank 失败    → 保留 RRF 原始排序
RAG 整体失败   → 退化为纯 AI 对话（不带知识库上下文）
AI 调用异常    → 返回兜底文案（照样流式输出）
Embedding 同步失败 → 只告警，不阻塞启动

每一级降级都要记日志，否则线上出问题根本无从排查。这套链路的代价是代码里到处是 try-catch，但它把“外部依赖的不可靠”和“用户体验的可靠”解耦了。

四、其他

  • 检索结果加应用级缓存（Caffeine，@Cacheable），但所有入库/删库操作必须 @CacheEvict——知识库运营同学改了文档，检索缓存不刷新就是事故。
  • 元数据过滤字段白名单 + 参数绑定。全文检索要拼 SQL，过滤字段名走固定白名单、值走 JDBC 参数绑定，别因为“这是内部接口”就拼接用户输入。
  • 参考来源区分类型（知识库 / 诈骗案例）并在回答中引用。这不只是体验问题——反诈场景下，“这个回答依据的是哪份材料”直接决定用户信不信你。
  • 入库即全量重建该文档的索引：先按 sourceType + sourceId 删旧 chunk 再写新 chunk，配合确定性 chunk ID，避免版本回滚、重新上传后向量库里留着僵尸数据。

五、总结

RAG 的核心不在模型，在检索链路的工程韧性。

具体的几条：

  1. 垂直领域别信纯向量，混合检索（关键词 + 语义）+ RRF 融合是性价比最高的第一步。
  2. 中文全文检索，确定性二元分词 + tsvector 生成列是 PostgreSQL 生态下最省事的对齐方案。
  3. 查询扩展只喂关键词通道，别污染向量通道。
  4. ReRank 是可开关的增强层，精排救不了烂召回。
  5. 外部模型全是不可靠依赖，降级链比主链路更值得投入。
  6. Nginx 缓冲、空流静默失败、降级也要保持流式协议一致。
